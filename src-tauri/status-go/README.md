# Stauri patch for `status-go`

`stauri-close-accounts.patch` is the only change Stauri makes to `status-go`.
It is a `git format-patch` file: readable in full in a few minutes, and
applicable to the pinned upstream commit.

```bash
git clone https://github.com/status-im/status-go.git
cd status-go
git checkout 766535cf336416a11a92f46faf4df5ac6af4a0b8
git apply /path/to/stauri-close-accounts.patch
git diff --stat          # 2 files changed, 39 insertions(+)
git diff                 # and this is the entire patch
```

A fork carrying the same change on a single branch:
`https://github.com/magnus-redkin/status-go/tree/stauri/close-accounts`
(diff against upstream: `.../compare/766535cf3...magnus-redkin:status-go:stauri/close-accounts`).

License — MPL-2.0, like `status-go`: the modified source is published here.

## Why

`status-go` opens the account-list database (`accounts.sql`) **once per
process**:

```go
func (b *StatusBackend) OpenAccounts() error {
	if b.multiaccountsDB != nil {
		return nil                       // <- every later call exits here
	}
	db, err := multiaccounts.InitializeDB(filepath.Join(b.rootDataDir, "accounts.sql"))
```

Meanwhile `UpdateRootDataDir` (called from `InitializeApplication`) *does*
change the root — the keystore path is resolved from it. The mismatch: the
account list stays in the **first** directory, while the keystore is looked
up in the new one.

In Stauri each network has its own data directory (`<data>/mainnet/`,
`<data>/sepolia/`), so switching networks means switching directories.
Without the patch a mainnet profile shows up under Testnet but cannot be
opened: its keystore is not under `sepolia/keystore`.

## What changes

| File | What is added |
|---|---|
| `pkg/backend/geth_backend.go` | `StatusBackend.CloseAccounts()` — closes the database, nils the field, detaches it from the node |
| `mobile/status.go` | the `CloseAccounts()` export |

`build/bin/statusgo-lib/main.go` (the bridge into `libstatus.so`) is
generated by `tools/generate-cbindings` from `mobile/status.go`, so no
separate edit is needed — the symbol appears on its own.

Call order from the host: `CloseAccounts()` → `InitializeApplication(newDir)`.
The second call opens `accounts.sql` in the new directory.

## What the patch does not do

- touches no crypto, transport, storage format, or password handling;
- adds no network calls or telemetry;
- changes no existing call: a host that never closes the database behaves
  exactly as before (`CloseAccounts` is idempotent and is not called by
  anything on its own);
- closes the **unencrypted** `accounts.sql`, which holds profile metadata —
  no keys live there. The keystore only "moves" because
  `InitializeApplication` re-sets `rootDataDir`.

## Verification

The symbol in a built library:

```bash
nm -D --defined-only build/bin/libstatus.so | grep -w CloseAccounts
# … T CloseAccounts
```

Behavior (one process, via `ctypes`):

1. `InitializeApplication(A)`, create a profile → one profile in `A`;
2. `InitializeApplication(B)` **without** `CloseAccounts` → still one
   profile (that is the bug);
3. `Logout`, `CloseAccounts`, `InitializeApplication(B)` → zero profiles,
   `B/accounts.sql` created.

This scenario was run against the built library: steps 2 and 3 gave 1 and 0
respectively.

## The vanilla library

The patch is optional for the application. The symbol is loaded through
`libloading` as optional (`src-tauri/src/core/inprocess.rs`): an unpatched
`libstatus.so` loads and works, every other flow is intact, and a network
switch returns an error that says to rebuild the library from
`src-tauri/status-go`. There is no silent behavior change.

## Lifetime

The change is a candidate for upstream: the reason for it is generic (a host
that changes its data directory without restarting the process). As soon as
`CloseAccounts` lands in `status-im/status-go`, the patch is dropped from the
build.
