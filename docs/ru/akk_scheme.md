# Схема АКК: Владелец — Канал — Комментарии

Документ фиксирует схему интерфейса «Автор → Канал → Комментарии» (АКК) и то,
как она ложится на возможности `status-go`, доступные **без форка** бэкенда.

Дополняет `architecture.md` (границы слоёв) и `providers_and_dapps.md`
(встраивание внешних данных).

## 0. Состояние на 2026-11-09

Схема реализована в основных частях и проверяется живьём по сценариям
A–E (News, по заявке, Issues, 1-1, ссылки) и Z (контакты и 1-1). Что есть в коде:

## 1. Задача и ограничение

| | |
|---|---|
| **Хотим** | Пользователь видит канал как ленту записей автора и может комментировать каждую запись |
| **Жёсткое ограничение** | Не форкать `status-go` |
| **Причина ограничения** | Форк — это постоянное сопровождение и повод для претензий со стороны авторов Status/Logos |
| **Важно** | Взаимодействие с `Community` под капотом не мешает: пользователь его не видит |

Схема должна пережить переход на Logos-core: чем меньше она опирается на
специфику `status-go`, тем дешевле будет миграция.

## 2. Почему не threads

В Status комментарии — это threads, и механизм существует:

```go
type Thread struct {
	ThreadID        string `json:"threadId"`
	ChatID          string `json:"chatId"`
	ParentMessageID string `json:"parentMessageId"`
	MessagesCount   uint
}
```

Но в `status-backend` они **выключены**, и это не настройка, а сборка:

```go
// pkg/services/ext/service.go — полный список опций мессенджера
options := []protocol.Option{
	protocol.WithPushNotifications(),
	protocol.WithDatabase(appDb),
	...
}
// WithThreads() отсутствует
```

Функция `WithThreads()` объявлена в `messenger_config.go` и **не вызывается
нигде** в репозитории.

Опасность не в том, что threads не работают, а в том, как именно они не
работают:

```go
// messenger.go, sendChatMessage
if !m.featureFlags.Threads {
	message.ThreadId = nil          // ← молча затирается
} else if message.GetThreadId() != "" { ... }
```

Отправка вернула бы `ok`, а сообщение легло бы в общий поток. Для пользователя
это выглядело бы как «комментарий отправился, но не появился».

**Вывод:** threads — цель на будущее (когда флаг включат в upstream), но не
средство достижения сегодня.

## 3. Что используем вместо: `responseTo`

В `common.Message` есть поле, которое работает без флагов:

```go
// Message.UnmarshalJSON принимает его напрямую:
ResponseTo string `json:"responseTo"`
...
m.ResponseTo = aux.ResponseTo
```

Единственная проверка при отправке:

```go
// messenger.go
if len(message.ResponseTo) != 0 {
	exists, err := m.persistence.MessagesExist([]string{message.ResponseTo})
	if exists[message.ResponseTo] == false {
		return nil, ErrInvalidResponseTo
	}
}
```

`MessagesExist` — это `SELECT id FROM user_messages WHERE id IN (...)`, **без
фильтра по чату**. То есть достаточно, чтобы родительское сообщение было у нас
в базе; принадлежность каналу не проверяется.

Этого хватает: комментарий — обычное сообщение с `responseTo`, указывающим на
запись канала.

| Свойство | threads | `responseTo` |
|---|---|---|
| Требует флага | да | **нет** |
| Требует форка | да | **нет** |
| Счётчик участников | есть | нет |
| Список тредов канала | `ChatThreads` | нет RPC |
| Метаданные (имя, счётчики) | `Thread` | нет |
| Поиск ответов | — | только через SQL (`MessagesByResponseTo`, RPC нет) |

## 4. Ключевое следствие: ответы видны в общем потоке

Ответ — это обычная строка в `user_messages` с тем же `local_chat_id`. Запрос
сообщений канала **не фильтрует** по `response_to`:

```go
// message_persistence.go, MessageByChatID
WHERE NOT(m1.hide) AND m1.local_chat_id = ? ...
```

Единственный фильтр по «вложенности» касается `thread_id`, и он явно
отключён при выключенных threads:

> *If threads are disabled, then we are backwards compatible and messages in
> threads are treated as normal messages, so we don't filter them out.*

**Значит: комментарий придёт и в ленту канала, и в панель комментариев.**

Это не дефект `status-go`, а следствие того, что комментарий технически —
обычное сообщение. Отсюда два обязательных правила интерфейса:

1. **Лента канала скрывает сообщения с `responseTo`.** Фильтрация на клиенте:
   `messages.filter(m => !m.responseTo)`.
2. **Панель комментариев показывает только их.** `messages.filter(m => m.responseTo === parentId)`.

Оба правила — клиентские, потому что серверного способа получить «только
ответы» по RPC нет. Это осознанная цена отсутствия форка.

## 5. Модель данных интерфейса

```ts
/** Запись канала: сообщение без responseTo. */
interface ChannelPost {
  id: string;
  chatId: string;
  from: string;
  text: string;
  timestamp: number;
  /** День вставки: есть ли у записи комментарии. */
  commentCount: number;
  isOwn: boolean;
}

/** Комментарий: сообщение с responseTo = родитель. */
interface Comment {
  id: string;
  parentId: string;
  from: string;
  text: string;
  timestamp: number;
  isOwn: boolean;
}

/** Состояние ленты канала. */
interface ChannelState {
  chatId: string;
  posts: ChannelPost[];
  /** Комментарии по родителю; ключ — id записи. */
  comments: SvelteMap<string, Comment[]>;
  /** Открытая панель комментариев (null — панель закрыта). */
  openFor: string | null;
  cursor: string;
  canPost: boolean;
}
```

`comments` держим картой, а не одним массивом: панель может открываться на
разных записях, и при переключении не хочется перезагружать всё.

## 6. Экраны

### 6.1 Левая колонка «Чат»

```
┌────────────────────────────────┐
│ Chat          [👤] [💬] [✎]    │  ← пригласить · ввести инвайт · новый канал
│ ┌────────────────────────────┐ │
│ │ 🔍 Поиск     │ │  ← всегда видна, в рамке; клик по лупе — фокус
│ └────────────────────────────┘ │
│ ◇ news-канал     │
│ ! Входящий контакт      │  ← запрос: Accept / Reject справа
│ ◇ request-канал · Logos         │
└────────────────────────────────┘
```

Иконки открывают **правую** панель, а не левую: левая остаётся списком.
Поиск фильтрует список по имени канала, имени сообщества и id. Ввод инвайта
в поиске **не разбирается**: ссылка вставляется в правую панель «Подключить
по приглашению».

### 6.2 Правая панель

Режим хранится в `chatsState.rightPanel`: `chat`, `contactInvite`,
`joinInvite`, `newChannel`. Выбор чата в списке возвращает `chat`.

| Режим | Что показывает | Компонент |
|---|---|---|
| `chat` | переписка выбранного чата, либо «Select a chat» | `ChatMain.svelte` |
| `contactInvite` | QR и ключ профиля (`zQ3…`) для добавления контакта | `ContactInvitePanel.svelte` |
| `joinInvite` | поле ссылки `status.app/cc/…` или `status.app/u/…` | `JoinInvitePanel.svelte` |
| `newChannel` | форма создания канала, описание — textarea | `CreateChannelPanel.svelte` |

Для входящего запроса (`active: false`, `lastMessage.contactRequestState = 1`)
`ChatMain` показывает экран «Accept / Reject» вместо переписки. Accept
принимает контакт и открывает чат; Reject отклоняет и возвращает панель к
«Select a chat».

## 7. Права: два разных вопроса

Их нельзя смешивать, иначе интерфейс будет обещать то, чего бэкенд не даст.

**Вопрос 1 — можно ли писать в канал.** Считается бэкендом:

```go
func (o *Community) CanPost(pk, chatID, messageType) (bool, error) {
	hasAccessToChat := o.CanView(pk, chatID)
	if !hasAccessToChat { return false, nil }
	if o.IsPrivilegedMember(pk) { return true, nil }
	member := chat.Members[crypto.PubkeyToHex(pk)]
	if member == nil && channelHasPermissions(...) { return false, nil }
	...
}
```

Результат уже приходит в `CommunityChat.canPost` и в `ChatItem.canPost`.
**Клик по сообщению не выдаёт права** — он либо открывает комментарии, либо
показывает, почему нельзя.

**Вопрос 2 — можно ли отвечать на запись.** Отдельного права нет: это то же
`canPost`. Ответ — обычное сообщение.

Значит логика интерфейса простая:

```
canPost == false  →  панель открывается (читать), поля ввода нет,
                     с объяснением
canPost == true   →  панель открывается, поле ввода активно
```

Отдельного механизма «получить права по клику» не существует и не требуется.
Если прав нет, их даёт только вступление в сообщество или токен.

## 8. Поток: от приглашения до комментария

```
1. Приходит ссылка
   status.app/c#<ключ>  ──►  сообщество, а не канал
                             (канальные приглашения отдельно не выдаются)

2. Просмотр
   spectateCommunity(id)
   → каналы читаются, canPost = false

3. Вступление
   requestToJoinCommunity
   → выбор адресов + пароль (подпись делает status-go)
   → результат: заявка, принятие приходит сигналом

4. После вступления
   canPost = true → поле ввода появляется

5. Клик по записи
   → комментарии этой записи (фильтр responseTo)
   → ввод доступен, если canPost

6. Отправка комментария
   sendChatMessage(chatId, text, communityId, responseTo = parentId)
```

**Важно про каналы:** deep link канала внутри сообщества имеет вид
`status-app://cc/<channel>#<community>`, но он ведёт в уже известное
сообщество. Публичные каналы Status (`#status`) — самостоятельны и не имеют
приглашений, только имя.

### 9.1 Сигнатура отправки

```ts
export async function sendChatMessage(
  port: number,
  chatId: string,
  text: string,
  communityId = '',
  responseTo = ''          // пустая строка — обычное сообщение
): Promise<any>
```

Поле `responseTo` кладётся на верхний уровень объекта — рядом с `chatId`, как
того ждёт `Message.UnmarshalJSON`.

### 9.2 Разделение сообщений

Одна функция, чтобы правило было в одном месте:

```ts
/**
 * Комментарий — сообщение с непустым responseTo.
 *
 * status-go не различает их на уровне канала: ответ лежит в той же таблице
 * и приходит в общем списке (MessageByChatID не фильтрует response_to).
 * Поэтому разделение — наша обязанность, и делать её надо ровно здесь.
 */
export function isReply(msg: { responseTo?: string }): boolean {
  return !!msg.responseTo && msg.responseTo.length > 0;
}
```

### 9.3 Подсчёт комментариев

Серверного счётчика нет. Считаем на клиенте по уже загруженной истории:

- при загрузке страницы сообщений группируем ответы по `responseTo`;
- счётчик показываем только для загруженных страниц;
- если история длинная, счётчик будет неполным — **это надо показывать
  честно**: «7 комментариев» может означать «7 из загруженных».

Альтернатива — не показывать число, а показывать сам факт: «Есть
комментарии». Меньше лжи при том же UX.

**Решение:** на первом шаге показываем факт, а не число. Число включим,
если появится способ получить его точно.

## 10. О фантазии с двумя каналами

Предложение: автор создаёт два канала — «главный» и служебный, а комментарии
физически лежат во втором, но выглядят как комментарии к первому.

**Работать это будет**, и вот честная оценка.

Что даёт выигрыш:

- ответы не попадают в общий поток — их никто не увидит в основном канале;
- можно раздать права по-разному: в главный — писать только автору, в
  служебный — писать всем;
- визуально это ровно АКК.

Цена:

| Проблема | Суть |
|---|---|
| Двойная доставка | пользователь подписан на два канала вместо одного |
| Связь «комментарий → запись» | всё равно через `responseTo`: связь по id сообщения, а не по каналу |
| История | порядок сообщений между каналами не гарантирован |
| Права | `canPost` надо проверять для служебного канала, а показывать для главного |
| Видимость | служебный канал придётся скрывать из списка чатов — а он там настоящий |
| Создание | автору нужно создать два канала и связать их; при ошибке — мусор в списке |
| Logos-core | в плоской модели каналов эта связка не переживёт миграцию |

Главное: **связь «комментарий → запись» и так идёт через `responseTo`**, а не
через канал. Второй канал не решает ни одной задачи, которую не решает первый,
кроме одной — «не показывать ответы в основном потоке».

А эту задачу решает одна строка фильтра на клиенте:

```ts
messages.filter(m => !isReply(m))
```

**Решение: второй канал не нужен.** Если позже окажется, что ответы должны
иметь другие права, чем записи, — вернёмся к этому. Сейчас это лишняя
сущность в модели, которую придётся скрывать от пользователя, и которая
сломается при переходе на Logos-core.

## 11. Границы схемы

Что схема **не** делает и почему:

| Не делаем | Причина |
|---|---|
| Вложенные комментарии (комментарий на комментарий) | `responseTo` это позволяет технически, но панель станет деревом. Первый шаг — плоский список |
| Уведомления о комментариях | нужен разбор `response_to` в сигналах, отдельная задача |
| Редактирование и удаление | есть в status-go, но не входит в АКК |
| Порядок «автор отдельно» | автор — это `msg.from`, фильтрация по нему на клиенте; отдельного «канала автора» не вводим |
| Права на комментарии отдельно от записей | см. §10 |

## 12. Проверено на живом бэкенде

Схема опиралась на три предположения. Все три проверены вызовами против
работающего `status-backend` (канал `#status`, 2026-11-04).

| # | Предположение | Результат |
|---|---|---|
| 1 | `responseTo` принимается без feature-флага | **подтверждено** — сообщение сохранено с `responseTo` = id родителя |
| 2 | Ответ приходит в общем списке канала | **подтверждено** — `chatMessages` вернул его наравне с остальными |
| 3 | Ссылка на сообщение из другого чата не отклоняется | **подтверждено** — отправка в другой канал с `responseTo` на запись `#status` прошла |

Третья была единственной, способной сузить схему до «комментарии только
внутри одного канала». Она не сузилась: `MessagesExist` действительно не
фильтрует по чату.

### Ещё один факт из проверки

`wakuext_sendChatMessage` возвращает в `result.messages` **и новый ответ, и
родительское сообщение**. Это значит, что после отправки комментария панель
можно обновить из ответа, не делая отдельный запрос истории.

### Замечание о неактивных чатах

Отправка в **неактивный** чат (`active: false`, например личная переписка, из
которой вышли) не создаёт сообщения и не возвращает ошибку: в ответе просто
нет нового сообщения. Для проверок это важно — ветку «ошибки нет, но
результата тоже нет» интерфейс обязан распознавать сам, по отсутствию
своего id в ответе.
