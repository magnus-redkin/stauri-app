# Архитектура Stauri

Документ описывает, как устроен Stauri «в целом»: из каких слоёв он состоит,
как они общаются и почему границы проведены именно так.

Дополняющие документы: `networks_and_balances.md` (путь баланса на экран),
`status_outdated_architecture.md` (почему `status-go` устроен сложно),
`providers_and_dapps.md` (внешние источники и dApp), `akk_scheme.md`
(схема «Автор → Канал → Комментарии»), `tests.md` (уровни тестов).

Обновлён 2026-11-08.

---

## 1. Главное решение: сайдкар вместо библиотеки

Stauri не линкует `status-go` как библиотеку. Он запускает `status-backend`
как **отдельный процесс** (sidecar) и общается с ним по двум каналам:

- **HTTP** (`http://127.0.0.1:<proxy>/statusgo/CallRPC`) — запросы;
- **WebSocket** (`ws://127.0.0.1:<proxy>/signals`) — асинхронные сигналы.

Причины ровно две:

1. **Жизненный цикл.** Падение или перезапуск `status-go` не должен утаскивать
   UI. Процесс можно убить и поднять заново, не трогая окно приложения.
2. **Версионирование.** Бинарник `status-go` собирается отдельно (Nix/Go),
   а фронтенд — на Svelte. Их можно обновлять независимо, пока контракт
   JSON-RPC не меняется.

Плата за это — управление процессом: `start_backend` / `stop_backend`,
PID-файл, убийство «зомби» при старте (`sidecar.rs`). Дополнительно:
`status-backend` и `libsds.so` должны быть собраны в **одном Nix-окружении**
(одна glibc, один ABI), иначе `status-backend` падает с `SIGSEGV` при загрузке
`libsds.so`.

**Версия бэкенда.** В `src-tauri/binaries/` лежит `status-go v10.35.0-167`.
Это важно помнить: исходники в Go-кэше модулей могут относиться к другой
версии, и набор RPC-методов в них отличается. Проверять сигнатуры следует по
исходникам именно этой сборки (`/home/michael/ETH/github.status-go`), а ещё
надёжнее — запросом к запущенному процессу.

## 2. Два прокси перед бэкендом

Между фронтендом и `status-backend` стоят два независимых процесса-прокси.
Это не украшение, а два разных требования.

### 2.1. Аутентифицирующий прокси (`auth_proxy.rs`)

`status-backend` не проверяет, кто к нему подключился: любой локальный процесс
может вызвать `settings_getSettings` (отдаёт seed-фразу) или `wallet_*`
(перевод средств). `CheckOrigin` в его WebSocket-обработчике возвращает `true`,
то есть не защищает и от сторонних веб-страниц. Loopback не изолирован между
пользователями машины.

Прокси слушает свой порт, требует заголовок `X-Stauri-Token` с секретом,
сгенерированным при старте из `/dev/urandom`, и только после проверки
пересылает трафик. Работает и для HTTP, и для WebSocket: после проверки
первого запроса соединение копируется в обе стороны, поэтому upgrade проходит
прозрачно.

Токен передаётся во фронтенд (`auth_proxy_token`), чтобы тот добавлял
заголовок. При XSS токен доступен — это осознанный компромисс: цель — закрыть
доступ **другим локальным процессам**, а при XSS у атакующего и без того есть
Tauri-команды.

**Практическое следствие:** везде, где в коде указан «порт бэкенда», имеется в
виду порт этого прокси. Ни фронтенд, ни Rust-модули не ходят в настоящий порт
`status-backend` напрямую.

### 2.2. RPC-форвардер (`rpc_proxy.rs`)

Локальный HTTP-сервер (предпочтительный порт `43057`) между `status-go` и
внешними RPC-провайдерами. Причина — залипание TCP-соединений в пуле
`status-go`: форвардер открывает новое соединение на каждый запрос
(`pool_max_idle_per_host(0)`) и ведёт себя как `curl`, а не как
`http.DefaultTransport`. Подробнее — в `networks_and_balances.md`.

С точки зрения фронтенда это просто команды (`start_rpc_proxy`,
`set_rpc_upstreams`, `stop_rpc_proxy`). Фронтенд не знает, что внутри
`reqwest`.

## 3. Слои

```text
┌──────────────────────────────────────────────────────────────┐
│ UI (Svelte 5)                                                │
│ routes/+page.svelte, sections/{wallet,profile,chat,…}        │
├──────────────────────────────────────────────────────────────┤
│ Сторы (Svelte 5 runes, .svelte.ts)                           │
│ statusStore, connectionStore, walletStore, sendStore,        │
│ ensStore, swapStore, chatsStore, contactsStore, …            │
├──────────────────────────────────────────────────────────────┤
│ Граница status-go (TypeScript)                               │
│ status/http.ts (транспорт), status/wallet.ts (кошелёк+ENS),  │
│ status/api.ts (реэкспорт), status/messaging.ts (чаты)        │
├──────────────────────────────────────────────────────────────┤
│ Tauri (Rust)                                                 │
│ sidecar, auth_proxy, rpc_proxy, transfer, ens, swap, router, │
│ market, providers, seed, updater, dapp, …                    │
├──────────────────────────────────────────────────────────────┤
│ Внешние источники                                            │
│ status-backend (HTTP+WS) · RPC-провайдеры · CoinGecko · RSS   │
└──────────────────────────────────────────────────────────────┘
```

Границы проведены по **времени жизни** и **частоте изменения**:

- **UI** меняется постоянно, зависит только от сторов.
- **Сторы** — единственное место с изменяемым состоянием; UI их читает и
  вызывает действия.
- **`status/http.ts`** — единственное место, где живёт транспорт, логирование
  и разбор ошибок JSON-RPC.
- **`status/wallet.ts`** — граница кошелька и ENS. Когда `status-go` уйдёт под
  Logos, менять придётся этот файл и его вызовы, а не весь фронтенд.
- **Tauri** — процессы, окна, локальные сокеты, подпись, запросы к внешним API.
- **`status-backend`** — «чёрный ящик» со своим состоянием и кэшами.

## 4. Поток данных

### 4.1. Запрос-ответ (HTTP)

```text
UI → действие стора → status/wallet.ts → http.ts → tauriFetch
→ 127.0.0.1:<auth-proxy>/statusgo/CallRPC  (заголовок X-Stauri-Token)
→ status-backend → JSON-RPC → ответ
← http.ts разбирает error, возвращает data
← стор обновляет $state
← UI перерисовывается
```

`statusFetch` — единственная точка, где:

- ошибки JSON-RPC (`error.message`) превращаются в `Error` с текстом;
- пустой ответ превращается в `{}`;
- **тела запросов и ответов не логируются**. Раньше печатались первые
  200 символов ответа, а `settings_getSettings` возвращает seed-фразу в поле
  `mnemonic` — фраза уходила в консоль webview при каждом открытии экрана с
  ней. Сейчас логируются имя метода, длительность, длина тела и — при ошибке —
  HTTP-статус без тела;
- маскирование пароля в логах пока не сделано (открытый TODO).

Сторы не разбирают HTTP-статусы и не знают про JSON-RPC. Если транспорт
сменится, правка будет в одном файле.

### 4.2. Сигналы (WebSocket): два потребителя

Сигналы `status-go` рассылает **во все** открытые WebSocket-соединения. Это
позволяет иметь двух независимых потребителей:

| Потребитель | Где | Какие сигналы |
|---|---|---|
| Фронтенд | `ws.ts` → `statusStore.processSignal` | `node.login`, `node.stopped`, `messages.new` |
| Rust | `router.rs`, своё соединение на время операции | `wallet.router.sign-transactions`, `wallet.router.transactions-sent` |

Фронтенд:

```text
status-backend → WS /signals → ws.ts → statusStore.processSignal(rawJson)
→ обновление $state
```

`processSignal` **синхронный** и не делает сетевых вызовов. Всё остальное он
молча игнорирует (кроме пуша в `statusState.events` для отладки).

Rust (`router.rs`):

```text
connect_signals()  ── своё WS-соединение через auth-прокси
wallet_getSuggestedRoutes(params)     → маршрут + uuid (синхронно)
wallet_buildTransactionsFromRoute(uuid) → ответ сигналом
   ⟶ ждём wallet.router.sign-transactions по нашему uuid
wallet_signMessage(hash, from, password)  × N
wallet_sendRouterTransactionsWithSignatures({uuid, signatures})
   ⟶ ждём wallet.router.transactions-sent
```

**Почему Router-сигналы разбираются в Rust, а не во фронтенде.** Router может
вернуть несколько транзакций (approve + основная), и `wallet_signMessage`
подписывает любые 32 байта, не зная, что это. Если бы хэши уходили в webview,
чужой скрипт мог бы попросить подписать любой из них. Поэтому хэши, пароль и
разбор подписи `{r,s,v}` не покидают Rust.

### 4.3. Внешние API

Прямые запросы из Rust (`reqwest`), не через `status-go`:

- `market.rs` — CoinGecko `/coins/markets` для вкладки «Маркет», кэш 60 с,
  необязательный `COINGECKO_KEY` из `.env`;
- `providers.rs` — RSS/Atom и страницы Telegram для внешних лент.

Цены для **общего баланса** кошелька идут другим путём — через
`wallet_fetchPrices` в `status-go` (см. §5.3), потому что там уже есть
сопоставление токенов с CoinGecko по `crossChainId`.

### 4.4. Состояние

Всё состояние — в `$state`-объектах сторов:

| Стор | Что хранит |
|---|---|
| `statusState` | Соединение, логин, аккаунты, сеть, сигналы |
| `connectionState` | Процесс соединения, выбранная сеть |
| `walletState` | Адрес, балансы, цены, метаданные, `rpcError` |
| `sendStore` | Перевод: шаг, пароль сессии, комиссия, хэш |
| `ensStore` | Регистрация имени: цена, залог, владелец |
| `swapStore` | Обмен: токены, сумма, котировка |
| `walletView` | Открытая вкладка кошелька |
| `chatsState`, `contactsState` | Чаты и контакты |

Правила:

- **Никакого состояния в компонентах**, кроме локального UI (открыта ли
  модалка, текст в поле).
- **Никаких прямых вызовов границы из UI** — только через действия сторов.
- **Стор не знает про UI.** Он возвращает данные и коды ошибок, UI решает, как
  их показать.

## 5. Ключевые подсистемы

### 5.1. Запуск и логин

Порядок — не стилистика, а требование из кэша RPC-клиентов `status-go`
(подробно в `networks_and_balances.md`):

Подключение (`connect()` в `connection.svelte.ts`) и вход (`login()`) — две
разные последовательности:

```text
connect()
  start_backend → initializeApplication → setAccounts
  → openWs → configureWalletRpc (форвардер + провайдеры)   ← ДО логина

login()
  loginAccount → node.login
  → applyNetworkMode (settings_saveSetting('test-networks-enabled?'))
  → configureWalletRpc (повторно)
  → [если modeChanged или wroteProviders] logout → node.stopped → loginAccount
  → startMessenger

loadWallet() в walletStore — отдельно и позже:
  wallet_startWallet → getAccounts → балансы → цены
  → опрос каждые 3 с
```

Провайдеры прописываются **до** логина намеренно: RPC-клиенты status-go
кэшируются по `chainID` и не инвалидируются, поэтому клиент, созданный
раньше записи, остался бы с прежним URL. Повторный вызов после логина
закрывает случай, когда узел стартовал внутри `loginAccount` и успел собрать
клиента раньше.

Режим сети (`applyNetworkMode`) — единственное, что нельзя сделать в
`connect()`: `settings_*` регистрируется в `initServices`, то есть после
старта узла, а узел стартует внутри `loginAccount`. Без этого профиль,
запущенный как «sepolia», считал бы mainnet-сети.

`connectionStore.svelte.ts` — фасад: реэкспортирует `connectionState`,
`connect`, `login`, `createAccount`, `disconnect` из `connection.svelte.ts`,
а также `configureWalletRpc` (`rpcConfig.ts`) и работу с сокетом (`ws.ts`).
Он же единственный, кто вызывает `loginAccount`; ни UI, ни `walletStore`
этого не делают.

### 5.2. Кошелёк: чтение

`walletStore` — самый сложный стор, потому что зависит от двух кэшей
`status-go` (RPC-клиенты и кэш балансов) и от метаданных токенов.

- **Адреса** берутся из `accounts_getAccounts` (фильтр `!chat`), а не из
  `wallet-root-address`.
- **Метаданные** (`symbol`, `decimals`) — из
  `wallet_getTokensForActiveNetworksMode` (ответ ~4.6 МБ, кэшируется на
  сессию), сопоставление по `(chainId, tokenAddress)`.
- **Опрос** — по таймеру: `forceRefresh` в
  `wallet_fetchOrGetCachedWalletBalances` игнорируется, единственный рабочий
  способ перезапросить балансы — `wallet_restartWalletReloadTimer`.
- **Три состояния** различаются в UI: пустой каталог / RPC недоступен / норма.

Вкладки кошелька: **Assets / Send / Receive / Buy / Swap** (Buy пока выключена,
Swap работает только в mainnet). Отдельная вкладка «Аккаунты» открывается из
левой панели. ENS-имя живёт в профиле (`EditProfile` → `EnsNameBlock`), а не в
кошельке: это свойство личности, а не счёта.

Assets группирует токены по `(symbol, chainGroup, decimals)`, где `chainGroup`
= EVM (Ethereum, Optimism, Arbitrum, Base), BSC (Binance) или `chainId`.
Неизвестные и тестовые сети получают **собственную** группу по номеру: раньше
все они попадали в `OTHER`, и пять тестовых ETH складывались в одну строку.

### 5.3. Общий баланс

Итог по основным сетям (Ethereum, Optimism, BNB Chain, Base, Arbitrum)
показывается в шапке кошелька с «≈». Считается в `utils/totalBalance.ts`:

- **тестовые сети не входят совсем** — сеполия-ETH не конвертируется в ETH;
- токены **без цены не выбрасываются**, а помечаются («часть токенов без
  цены»), иначе полный кошелёк с новым токеном показал бы `≈ $0`;
- токены с `hasError` не считаются нулём;
- баланс делится на `10^decimals` в `bigint`, и только потом переводится в
  число — `number` теряет точность уже на 16 значащих цифрах.

Цены приходят из `wallet_fetchPrices`. Ключ там `chainId-адрес` через
**дефис**, а не двоеточие, как в остальном коде: на двоеточии бэкенд молча
ничего не найдёт.

### 5.4. Подпись: всё в Rust

Три денежные операции имеют одну и ту же форму: наружу торчит **намерение**,
а последовательность вызовов, пароль и подпись остаются в Rust.

| Операция | Команда | Файл |
|---|---|---|
| Перевод ETH/ERC-20 | `send_transfer`, `estimate_transfer_fee` | `transfer.rs` |
| Регистрация ENS | `register_ens_name`, `get_ens_quote` | `ens.rs` |
| Обмен | `swap_tokens`, `get_swap_quote` | `swap.rs` |

Перевод — три синхронных вызова:

```text
wallet_buildTransaction(chainID, sendTxArgs)   → messageToSign, txArgs
wallet_signMessage(messageToSign, from, pass)  → подпись
wallet_sendTransactionWithSignature(chainID, "WalletTransfer", txArgs, sig)
```

Регистрация и обмен идут через Router — их общий механизм (соединение к
`/signals`, ожидание сигналов, разбор подписи на `{r,s,v}`) вынесен в
`router.rs`. Дублировать его в двух модулях значило бы гарантировать
расхождение.

**Почему это принципиально.** `wallet_signMessage` подписывает любые 32 байта
ключом кошелька и не знает, что это за байты. Если бы эта последовательность
жила в webview, любая XSS получила бы и пароль, и универсальную машинку
подписи: чужой скрипт мог бы подписать собранную им транзакцию «переведи всё
на этот адрес». Тот же принцип применён к seed-фразе (`seed.rs`) и
обновлениям (`updater.rs`).

**Пароль** приходит от фронтенда один раз за сессию (как в мобильном Status),
хранится в памяти стора, на диск не пишется и стирается при выходе из
аккаунта. В Rust он живёт только внутри вызова.

### 5.5. Комиссия сети

`estimate_transfer_fee` собирает транзакцию тем же кодом, что и отправка
(`send_args`), и читает из неё `gas` и `gasPrice` — цифры ровно те, что уйдут.
Отдельного метода оценки в `status-go` для этого пути нет.

Известное ограничение: на тестовых сетях `eth_estimateGas` занижает лимит
(21000 против фактических ~204 600), поэтому в интерфейсе сумма подписана как
оценка. Для обмена и регистрации комиссия берётся из собранного маршрута
(`TxTotalFee`); если маршрут не собрался, показывается `null` — «неизвестно»,
а не ноль.

### 5.6. Market

`market.rs` (Rust) + вкладка «Маркет». С `status-go` не связано:
`fetch_market_data` делает `reqwest` к CoinGecko, кэширует на 60 секунд,
возвращает `Vec<MarketCoin>`. Числовые поля — `f64` (CoinGecko отдаёт float),
`#[serde(default)]` защищает от отсутствия `price_change_percentage_24h`.

Рыночные данные **не идут через `status-go`**: тот умеет их отдавать, но это
тянет зависимость от `market-proxy` и его кэшей.

### 5.7. dApp-окна

`open_dapp` создаёт отдельное окно с `WebviewUrl::External`. Это изоляция:
dApp не имеет доступа к `window.__TAURI__` главного окна, и его падение не
утаскивает Stauri. Внешние ссылки открываются системным обработчиком
(`opener.rs`), а не внутри webview.

### 5.8. Сборка и релиз

`scripts/release.sh` собирает AppImage:

1. `pnpm tauri build`. Бандлинг включается самим скриптом: в
   `tauri.conf.json` стоит `"targets": []`.
2. Вручную собирается `AppDir`: `status-backend` в `usr/bin/`, `libsds.so` в
   `usr/lib/`, патч интерпретатора на системный загрузчик, `RPATH=$ORIGIN`,
   `AppRun` с очищенным `LD_LIBRARY_PATH`.
3. `linuxdeploy` запускается с `NO_STRIP=1`.
4. Проверяется, что `libsds.so` внутри AppImage и что `status-backend`
   запускается под унаследованным `LD_LIBRARY_PATH`.

`status-backend` и `libsds.so` **не пересобираются** в `release.sh` — они
должны быть заранее собраны в Nix и лежать в `src-tauri/binaries/`.

### 5.9. Обновления

Проверка и установка — в Rust (`updater.rs`), а не в JS-плагине: webview —
самое уязвимое место, и `updater:default` дал бы странице право самой
запускать установку. В `capabilities/default.json` этого permission нет,
фронтенд ходит через `check_for_update` и `install_update`.

Порядок релиза: сгенерировать ключ (`pnpm tauri signer generate`), положить
публичную часть в `tauri.conf.json`, собрать с
`TAURI_SIGNING_PRIVATE_KEY_PATH`, загрузить `AppImage`, `.sig` и `latest.json`.
`release.sh` строит `latest.json` с ключом `linux-x86_64` — так называется
платформа в `tauri-plugin-updater`, менять ключ нельзя.

На Linux файл подменяется на месте, поэтому после установки нужен перезапуск.

## 6. Права и ограничения окна

CSP **настроена**, но не в Tauri, а в SvelteKit — `svelte.config.js` →
`kit.csp`. В `tauri.conf.json` стоит `"csp": null` намеренно: Tauri при
`csp` != null переписывает HTML через `set_csp`, и две политики
перемножаются по правилам CSP, причём `script-src 'self' 'unsafe-inline'`
из Tauri обнулил бы хеш SvelteKit.

`mode: 'auto'`: в продакшене SvelteKit хеширует инлайн-бутстрап и вставляет
`content-security-policy` meta-тегом в `build/index.html`, в dev —
проставляет nonce. Действующие директивы:

- `script-src 'self'` + хеш бутстрапа — **без** `unsafe-inline`, то есть
  посторонний скрипт из ответа `status-go` или фида не выполнится;
- `style-src 'self' 'unsafe-inline'` — нужно для Tailwind и инлайн-стилей
  Svelte;
- `img-src` — только `self`, `data:`, `blob:` и два CDN (логотипы токенов,
  картинки Market);
- `connect-src` — `127.0.0.1` (HTTP и WS), GitHub, `ipc:`;
- `object-src 'none'`, `base-uri 'self'`.

Второй слой — `capabilities/default.json`: `websocket:default`,
`core:default`, закрытие окна и HTTP **исключительно** к
`http://127.0.0.1:*`.

Практическое следствие, на котором уже спотыкались: ресурс с чужого CDN,
не перечисленного в `img-src` (например, сервис генерации QR), в webview не
загрузится, и это выглядит как «сломанная функция». Поэтому QR рисуется
локально, а логотипы токенов загружает Rust и отдаёт через `img-src`
разрешённые домены либо локально нарисованные данные.

**Что CSP не закрывает.** Она запрещает исполнение чужого скрипта, но не
защищает от скрипта, который уже внедрён в наш бандл или получен через
разрешённый канал. Поэтому пароль сессии, токен прокси и seed-фраза остаются
компромиссами, описанными в §5.4 и в `wallet_plan.md`: они доступны коду,
который исполняется в webview, и это осознанно.

Открытые задачи этого раздела — в `docs/PLAN.md`.

## 7. Почему именно так (альтернативы)

| Альтернатива | Почему не выбрана |
|---|---|
| Линковать `status-go` как библиотеку | Падение бэкенда = падение UI; версии жёстко связаны |
| Вызывать `status-go` напрямую из JS | Нет `reqwest`/`tokio`, нет управления процессами, нет подписи в безопасном месте |
| Держать всё состояние в одном сторе | Сторы начинают зависеть друг от друга; тесты усложняются |
| Подписывать транзакции в webview | XSS получает пароль и универсальную машинку подписи |
| Общаться с блокчейном напрямую из UI | Нет keystore, нет мультичейна; `status-go` всё равно нужен для мессенджера |
| Использовать готовый `status-desktop` | Монолит QML; нет модульности, нет dApp-изоляции, нет Svelte |
| Брать рыночные данные из `status-go` | Тянет `market-proxy` и его кэши |
| Форкнуть `status-go` | Слишком много критики от авторов SIM/Logos; проще жить на публичном контракте |

## 8. Инварианты архитектуры

1. UI не вызывает границу `status/*` напрямую — только через сторы.
2. `status/http.ts` — единственное место с транспортом и разбором ошибок.
3. Тела ответов `status-go` не логируются (там seed-фраза).
4. `processSignal` синхронный; асинхронные реакции запускаются отдельно.
5. `connectionStore` — единственный, кто знает порядок запуска и логина.
6. Пароль и подпись не покидают Rust; наружу торчит намерение.
7. Router-сигналы разбирает Rust, а не webview.
8. dApp-окна изолированы от главного окна.
9. Rust-команды — единственный способ общаться с ОС и с внешними API.
10. Market не зависит от `status-go`; его можно отключить, не ломая кошелёк.
11. `status-backend` и `libsds.so` — из одного Nix-окружения.
12. Сеть и режим (mainnet/testnet) задаются **дважды**: конфигом Rust
    (`STAURI_NETWORK`) и флагом `test-networks-enabled?` для `status-go`.
    Это разные вещи, и забыть вторую — уже случалось.
13. Внешние адреса проверяются на **каждом** переходе: исходный
    `validate_external_url` и каждый редирект по отдельности
    (`fetch_following_redirects`). Проверка только первого адреса
    декоративна — встроенное следование `reqwest` шло бы куда угодно.
14. Секреты стираются при выходе из аккаунта: пароль (`resetSend`) и
    seed-фраза (`clear_seed`). Фраза не должна переживать смену профиля.

## 9. Что менять при добавлении функции

**Метод `status-go`, отвечающий результатом** (например, новое чтение):

1. Обёртка в `status/wallet.ts` (или `messaging.ts` для чатов).
2. Действие в сторе.
3. UI читает стор.
4. Тесты: юнит-тесты утилит/стора, при необходимости — тест `statusFetch`.

**Метод, отвечающий сигналом**: сигнал разбирается там, где операция
оркестрируется. Если это денежная операция — в Rust (`router.rs`), по образцу
`ens.rs` и `swap.rs`. Если UI-событие (`messages.new`) — в `processSignal`.

**Внешний API:**

1. `src-tauri/src/<module>.rs` — команда с `reqwest` и кэшем.
2. `invoke('<command>')` из стора (аргументы верхнего уровня — **camelCase**,
   поля внутри `request` — snake_case по serde).
3. UI рендерит.
4. Тесты: чистую логику — юнит-тестами, запрос — ручной проверкой.

**Денежная операция:** команда Rust, возвращающая только результат
(хэш/сумму). Никаких «подпиши вот это» наружу.
