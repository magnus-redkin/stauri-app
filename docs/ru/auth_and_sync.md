# Вход, создание профиля и синхронизация устройств

Как пользователь попадает в Stauri и как его профиль оказывается на втором
устройстве: какие секреты существуют, где они лежат, что происходит при создании,
восстановлении по сид-фразе и при передаче на другое устройство.

Код: `src/lib/entry/entryFlow.ts` (правила переходов), `src/routes/+page.svelte`
(состояние и обработчики), `src-tauri/src/credentials.rs` (PIN и конверт),
`src-tauri/src/pairing.rs` (local pairing).

---

## 1. Три секрета

| Секрет | Что защищает | Кто знает | Где живёт |
|---|---|---|---|
| **Сид-фраза**, 12 слов | право владеть профилем где угодно | только пользователь | нигде; показывается при создании |
| **Пароль профиля**, 32 символа | шифрует локальную базу status-go | никто | зашифрован в конверте |
| **PIN**, 4–12 цифр | конверт с паролем | пользователь | нигде; из него выводится ключ |

Держать в голове нужно две вещи: сид-фразу — навсегда, она переезжает на любое
устройство, и PIN — на каждый запуск. Пароль базы не знает никто, и это не
недосмотр: его генерирует приложение, и человеку он не нужен ни разу за всё время
жизни профиля.

Исключение — профили, заведённые до этой схемы. Их открывает пароль, который
пользователь когда-то придумал сам. При первом входе такой профиль получает PIN и
становится обычным (§6).

### PIN — свойство устройства, а не профиля

На телефоне и на десктопе у одного профиля разные PIN, и это правильно. Конверт
привязан к устройству; передаётся не секрет, а сам профиль. Сид-фраза одна, PIN —
сколько устройств, столько и PIN. Одинаковый PIN на всех устройствах не
поддерживается и не планируется.

## 2. Где что лежит

Данные разнесены по сетям: профили mainnet и testnet друг друга не видят.

```
<data-dir>/<сеть>/                                        базы и keystore профилей
<data-dir>/credentials/<сеть>/<keyUid>/envelope.json      PIN и зашифрованный пароль
<data-dir>/credentials/<сеть>/<keyUid>/attempts.json      счётчик неверных PIN
```

`keyUid` — 64 шестнадцатеричных символа, он же имя папки keystore. Значение
проверяется по белому списку и **нормализуется к нижнему регистру**: без этого
`0xAB…` и `0xab…` завели бы два разных каталога для одного профиля, и PIN,
положенный в один, не нашёлся бы во втором. Это не «очистка» строки, а отказ:
`../` должен быть отвергнут, а не исправлен, потому что эти значения становятся
компонентами пути.

### Конверт

```json
{ "version": 2, "backend": "android-pin", "kdf": {…}, "salt": "…", "nonce": "…", "ciphertext": "…" }
```

- **Argon2id**: 64 МиБ памяти, 3 прохода, 1 поток. Параметры записаны в самом
  конверте, чтобы будущая сборка открыла старый файл после смены значений по
  умолчанию.
- **AES-256-GCM**: соль 16 байт, nonce 12 байт, ключ 32 байта.
- Неверный PIN рушит тег аутентификации. Сравнивать нечего, подделать нечего, и
  отличить «неверный PIN» от «испорченный файл» снаружи невозможно — так и задумано.

Зачем такая дорогая функция: у четырёхзначного PIN десять тысяч вариантов, и с
дешёвым хэшем их перебирают за секунды. Memory-hard KDF превращает перебор в годы.
PIN слабый по построению — он короткий, потому что вводится на телефоне, — и KDF
ровно это компенсирует.

Читая конверт, приложение не верит написанному в нём:

- **версия** должна совпадать с текущей;
- **backend** должен быть свой (`android-pin` на телефоне, `desktop-pin` на
  десктопе) — файл с другой платформы отвергается, а не разбирается как свой;
- **параметры KDF** проверяются по диапазону. Это вход, а не константа: файл с
  `memory_kib = 4_000_000` уронил бы процесс при следующем вводе PIN, а файл с
  `memory_kib = 8` сделал бы перебор дешёвым.

Запись тоже не «на глазок»: файл пишется во временное имя, сбрасывается на диск и
переименовывается поверх цели, каталог синхронизируется следом. Конверт,
записанный наполовину, — это профиль, который не открыть; `truncate` по живому
файлу давал бы ровно такое окно. Попытка записи счётчика идёт **до** конверта, чтобы
не оставить новый конверт за исчерпанным счётчиком.

## 3. Вход на устройстве, где профиль уже есть

```
запуск → список профилей → PIN → Home
```

1. Приложение поднимает status-go и читает профили **выбранной сети**.
2. Нажатие на профиль: спрашивается состояние слота (`credential_pin_state`).
3. PIN раскрывает конверт (`credential_open_pin`), полученный пароль уходит в
   `LoginAccount`.
4. Сессия открыта по PIN — значит, её можно запирать (§7).

Нет профилей — нет и клавиатуры PIN: запирать нечего.

### Состояние слота решает, какой экран показать

Клавиатура показывается не всегда. Состояние читается **до** неё, иначе «после
лимита — сразу к фразе» не работало бы: пользователь видел клавиатуру, отказ
приходил только по нажатию, и отличить лимит от опечатки было нельзя.

| Состояние | Экран | Почему |
|---|---|---|
| `missing` | пароль | профиль до схемы PIN, пароль знает пользователь |
| `ready` | клавиатура PIN | обычный случай |
| `locked-out` | фраза | конверт больше не откроется |
| `damaged` | фраза | конверт есть, но не читается |

`damaged` — это не «нет PIN». Пароль под таким конвертом сгенерирован приложением,
его не знает никто, поэтому экран пароля был бы дверью, которая не открывается.
Такое состояние даёт не только порча файла, но и профиль, принятый по pairing, у
которого PIN так и не задали (§8.4).

### Правила

| Правило | Значение | Где |
|---|---|---|
| длина PIN | 4–12 цифр | `credentials.rs`, дублируется в `entryFlow.ts` |
| попыток до блокировки | 10 | `MAX_ATTEMPTS` |
| неверный PIN | счётчик +1, в сообщении остаток попыток | `open_pin` |
| верный PIN | счётчик сбрасывается | `open_pin` |

Счётчик увеличивается **до** ответа: процесс, убитый посреди попытки, не должен её
отменить. Попытки сериализуются мьютексом — иначе десять параллельных вызовов
прочли бы одно и то же значение и записали один и тот же плюс один. А счётчик,
который не читается как JSON, считается исчерпанным: повреждённый файл не должен
дарить новые десять попыток.

## 4. Создание профиля

```
вход → Create Profile → (пароль генерируется) → PIN → повторить PIN → сид-фраза → Home
```

1. **Пароль генерируется** в вебвью: 32 символа, только `crypto.getRandomValues`,
   по одному символу каждого класса (заглавная, строчная, цифра, знак), затем
   перемешивание. Без гарантированных классов строка случайно могла бы не пройти
   проверку правил пароля — а исправить её пользователь не смог бы, потому что
   никогда её не видит.
2. **`CreateAccountAndLogin`** создаёт профиль и сразу логинит. Поэтому экран выбора
   PIN удерживается отдельным условием в рендере — иначе он исчез бы до ввода.
3. **PIN спрашивается после создания**, а не до: `keyUid` известен только из ответа
   status-go, а конверт лежит под ним.
4. **PIN вводится дважды.** Опечатка зашифровала бы пароль под значением, которого
   владелец не знает; отменить это нечем — только сид-фразой.
5. **Сид-фраза показывается и проверяется** (`CreateSeed`): слова выдаются по одному
   через `seed_word(index)`, ответы сверяет Rust (`verify_seed_answer`), целиком
   фраза в вебвью не попадает. При уходе с экрана `clear_seed` стирает её из памяти
   процесса.
6. **Сохранение фразы возвращает на Home.**

Экран сид-фразы обязателен: PIN невосстановим, и фраза — единственный путь назад.

## 5. Восстановление по сид-фразе

```
вход → I already have a profile → Enter recovery phrase → 12 слов → пароль → Home
```

Пароль здесь задаёт пользователь: восстановление создаёт новую локальную базу, и её
надо чем-то зашифровать. Это другой пароль, не тот, что был на устройстве, где
профиль создавали.

Приложение различает два случая по `keyUid`, выведенному из фразы:

- **профиля здесь нет** — обычное восстановление через `RestoreAccountAndLogin`;
- **профиль есть, но пароль не подходит** — `LocalProfileLockedError`. Это не ошибка
  ввода: профиль лежит здесь под другим паролем, и подобрать его нельзя. Экран
  предлагает подтверждённое удаление локальной копии и восстановление заново
  (`resetLocalProfileAndRestore`). История сообщений и настройки этого устройства
  при этом теряются — предупреждение показывается до нажатия.

Ловушка для того, кто будет это отлаживать: `RestoreAccountAndLogin` отвечает
`{"error":""}` и при ошибке тоже. Настоящий результат приходит сигналом
`node.login`. Принять синхронный ответ за успех — значит однажды «успешно»
восстановить профиль, который не восстановился.

## 6. Профиль, созданный до схемы PIN

У такого профиля конверта нет вообще, и пароль знает только пользователь.

```
список профилей → пароль → PIN → повторить PIN → Home
```

Пароль спрашивается **один раз за всё время**: сразу после успешного входа
открывается выбор PIN, и профиль становится обычным. Сид-фраза повторно не
показывается — её сохранили, когда профиль создавали.

Это же состояние возникает после восстановления по фразе (§5): профиль открыт
паролем, которого нет в конверте. До ближайшего запуска он живёт на пароле, а на
следующем старте проходит тот же путь и получает PIN.

## 7. Блокировка при уходе в фон

PIN защищает запуск. Вторая половина — защита от того, кто взял уже разблокированное
устройство: при уходе приложения интерфейс закрывается клавиатурой PIN.

- **Триггеры** — `visibilitychange` (`hidden`) и `blur`, на обеих платформах. WebView
  на Android не всегда сообщает первый, а второй приходит надёжно; на десктопе
  `blur` окна — это и есть «пользователь отошёл». Блокировка идемпотентна, двойной
  вызов ничего не стоит.
- **`blur` слишком ретив.** Закрытие экранной клавиатуры тоже его вызывает — а это
  происходит сразу после ввода PIN. Поэтому в первые полторы секунды после удачного
  входа `blur` игнорируется, и только пока страница видима. Уход в другое приложение
  приходит как `hidden` и запирает немедленно, без всяких поблажек.
- **Backend не разлогинивается.** Соблазн сделать `Logout` понятен, но logout
  останавливает мессенджер, и каждый переход между приложениями стоил бы
  пересинхронизации при возврате. Данные защищает клавиатура впереди и стирание
  пароля из памяти (`clearSessionPassword`): подписать без PIN нельзя, а база и так
  зашифрована на диске.
- **Честно об ограничении.** Пароль стирается присваиванием пустой строки. В
  JavaScript строки неизменяемы, и гарантировать затирание старой копии в куче
  нельзя — `TextEncoder` и перезапись буфера тут ничего не меняют. Важно время
  жизни: пароль существует, только пока сессия разблокирована, и в `localStorage` он
  не уходит ни под каким ключом.
- **Разблокировка идёт через тот же `openPin`**, поэтому лимит попыток общий:
  перезапуском приложения его не обойти.
- **Профиль, открытый паролем** (§6, до появления PIN), не запирается: спрашивать
  PIN, которого нет, — тупик.

## 8. Передача профиля на другое устройство

### 8.1. Роль определяется состоянием, а не намерением

| Роль | Кто это | Что делает |
|---|---|---|
| **Sender** | устройство, где профиль открыт | показывает код, отдаёт профиль |
| **Receiver** | пустое или новое устройство | вводит код, принимает профиль |

Отправитель — всегда залогиненное устройство: передаются ключи, а они есть только у
него. Обратной ситуации, когда профиль приезжает на устройство, которое уже
залогинено, схема не предусматривает.

### 8.2. Строка подключения — единственный канал

status-go даёт пять вызовов, и каждый нужен ровно один раз:

```rust
GetConnectionStringForBootstrappingAnotherDevice     // отправитель: показать код
GetConnectionStringForBeingBootstrapped              // приёмник: показать код
InputConnectionStringForBootstrapping                // приёмник: прочитать чужой
InputConnectionStringForBootstrappingAnotherDevice   // отправитель: прочитать чужой
ValidateConnectionString                             // проверить, ничего не запуская
```

Строка — несколько сотен символов base58 через двоеточие: адрес, порт, публичный
ключ, ключ шифрования, идентификатор установки. Она же и аутентифицирует передачу:
клиент проверяет, что сертификат сервера подписан именно тем ключом, что лежит в
строке, и пиннит его. Чужой в той же Wi-Fi, не зная строки, за второе устройство
себя не выдаст.

**Автопоиска устройств нет, и это не упущение.** В status-go `PeerNotifier.Search`
на Android выходит сразу, с комментарием «Sorry Android»: mDNS-маяк там отключён.
Экран «ищем устройства в сети» на телефоне не нашёл бы ничего. Поэтому одна сторона
всегда показывает строку, другая её вводит.

Доставка — показ с кнопкой «копировать» и обычное поле ввода, куда строка
вставляется долгим нажатием. Отдельной кнопки «вставить» нет намеренно:
`navigator.clipboard.readText()` в WebView требует разрешения и при отказе молчит
вместо того, чтобы сообщить об ошибке.

Выбор «по Wi-Fi» и «по USB» — только оформление. status-go всегда соединяется по TCP
в локальной сети; различается лишь то, как строка попадает с одного экрана на другой.

### 8.3. Шесть цифр, которые сверяют люди

Строка — секрет, а не просто адрес. Кто её прочитал, пока сервер жив, может забрать
профиль. Поэтому обе стороны показывают по шесть цифр, выведенных из ключа шифрования
внутри строки, и человек их сверяет.

- Обе стороны считают одно и то же над одними байтами. Реализовано в Rust
  (`pairing.rs`), не в вебвью: вторая реализация на JavaScript была бы вторым
  способом ошибиться, и расхождение выглядело бы как атака.
- Строка, подменённая по дороге, даёт другие цифры. Не совпали — передачу не
  начинают.
- На приёмнике это два нажатия, а не одно: сначала «показать код сверки», и только
  после совпадения — «начать передачу». Случайно отправить не тот код нельзя.

**Чего цифры не делают.** Они ловят подмену, но не кражу: кто видел строку целиком,
использует её как есть, и цифры у него совпадут. От этого защищают другие две вещи:
короткое время жизни кода и PIN перед его показом.

### 8.4. Пароль приезжает вместе с профилем

В полезной нагрузке status-go (`LocalPairingPayload.password`) едет **пароль
отправителя**, и приёмник сохраняет ключи именно с ним. Приходит он не в ответе
вызова, а сигналом `received-account`:

```json
{"type":"localPairing","event":{"type":"received-account","data":{"account":{…},"password":"…","chatKey":"…"}}}
```

Поэтому подписка на сигналы оформляется **до** запуска передачи: событие может
прийти раньше, чем вызов вернётся, и подписчик, пришедший следом, прождёт пять минут
то, что уже случилось.

Пароль **не попадает в вебвью**. `pairing_receive` кладёт его во временный слот в
памяти Rust, а фронтенд получает только `key_uid` и имя. Когда пользователь выбрал
PIN, вызывается `credential_save_pin_from_pending` — единственный путь пароля на
диск, уже зашифрованным. Дальше страница читает его обратно через `openPin`: если PIN
действительно открывает конверт, это и есть проверка, что он сохранился правильно.

Ушёл с экрана PIN, не задав его, — пароль забывается (`credential_forget_pending`).
Профиль на диске остаётся, но открыть его нечем: это состояние `damaged` из §3, и
путь назад один — сид-фраза.

Показать пароль пользователю бессмысленно в любом случае: 32 случайных символа никто
не перепишет.

### 8.5. История сообщений — по выбору

Поле `messageSyncingEnabled` в конфиге отправителя включает перенос переписки. По
умолчанию оно выключено, и галочка на экране так и подписана: уедут все сообщения с
этого устройства, без ограничения по дате. status-go в собственном исходнике
называет это решением о приватности, которое пользователь принимает осознанно, — и
это не перестраховка: окна «последние N дней» там нет, батчи по сто сообщений
уходят из всей базы.

Вложения отдельно не передаются: медиа лежит на CDN, а в сообщениях хранятся ссылки
и метаданные.

Флаг читается только на стороне сервера, то есть у устройства с профилем. Поэтому и
направление остаётся таким, какое есть: залогиненное устройство показывает код.
Поменять его местами — значит потерять историю без патча библиотеки.

### 8.6. Срок жизни кода

Код живёт пять минут: `serverConfig.timeout` в конфиге отправителя. Отсчёт идёт от
старта сервера, и по истечении сервер закрывается — уже начатую передачу он
дожимает, но новую строку с этого момента не примет. Для человека это значит: пока
код на экране, он рабочий; ушли с экрана или провозились — начните заново.

Пять минут — не случайное число: это же значение status-go использует в своих тестах
pairing.

### 8.7. Порядок действий

**Отправка (устройство с профилем):**

Профиль → «Show this device's code» → **PIN** → строка и шесть цифр → отметить
галочку истории, если она нужна → передать строку второму устройству.

**Приём (новое устройство):**

Вход → «I already have a profile» → «Sync with another device» → вставить строку →
«Показать код сверки» → сверить цифры → «Цифры совпали — начать передачу» → задать
PIN дважды → Home.

Строку не пересылают в мессенджерах. Именно так она и утекает: код, отправленный
себе в чат, к моменту, когда им пользуются, уже видели не только вы.

### 8.8. Чего пока нельзя

- **Остановить сервер отдельной командой.** Экспорт status-go для этого не
  подключён, и кнопка «назад» сервер не гасит. Начатую отправку доводят до конца
  либо перезапускают приложение.
- **Перевернуть направление.** Новое устройство показывает код, основное вводит —
  так работают и Signal, и Status. У нас наоборот, потому что при перевёрнутом
  направлении сервером становится пустое устройство, а флаг истории читается только
  там; история в этом случае не поедет (§8.5).
- **Подтвердить передачу владельцем.** При нынешнем направлении профиль уезжает
  тому, кто знает строку. Защита — срок жизни и PIN перед показом, а не согласие
  владельца на самом переносе.

## 9. Отладка

Трасса пишется в `bridge-trace.log` в каталоге данных приложения. Пароли и
сид-фразы туда не попадают — только длины и результат.

```
credential pin saved network=mainnet key=0xcbae7ed2
credential pin open network=mainnet key=0xcbae7ed2 ok=false
credential pin saved from pairing key=0xcbae7ed2
note {"kind":"create","len":32,"sha256_16":"…"}
note {"kind":"login","len":32,"sha256_16":"…"}
pairing sender started key=0xcbae7ed2 stringLen=412 syncMessages=true
pairing received account key=0xcbae7ed2 passwordLen=32
```

Как читать `note`: `len` — длина пароля (32 — сгенерированный, короче — заданный
вручную), `sha256_16` — первые шестнадцать символов хэша, чтобы отличить одно
значение от другого, не раскрывая его.

На Android:

```
adb logcat -s stauri
```

Release-сборка не отлаживаема, поэтому `run-as` к файлу трассы не пустит — читать её
там можно только через logcat.

Отсутствие строк `credential pin` при живом входе означает, что профиль пошёл по
парольному пути. Это первый вопрос при любом «профиль не открывается».

## 10. Что ещё не сделано

1. **Живая передача между двумя устройствами не прогонялась.** Проверены сборка,
   разбор строки и событий, отсутствие падений.
2. **Отпечаток пальца.** Планируется как ускорение поверх PIN: ключ в Android
   Keystore с `setUserAuthenticationRequired(AUTH_BIOMETRIC_STRONG)` разблокирует
   конверт, PIN остаётся запасным входом. Не вместо PIN — иначе потеря отпечатка
   означала бы потерю профиля.
3. **Смена PIN.** Конверт можно только создать или удалить вместе с профилем.
4. **QR-код.** Строка подключения пока передаётся копированием.
5. **Остановка pairing-сервера** и **переворот направления** — см. §8.8.
